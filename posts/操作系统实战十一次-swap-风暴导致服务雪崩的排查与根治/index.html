操作系统实战（十）：一次 Swap 风暴导致服务雪崩的排查与根治

生产环境里最隐蔽的一类故障，往往不是 CPU 打满，也不是网络抖动，而是内存悄悄被压到瓶颈后引发的 Swap 风暴。本文以一次真实的"服务雪崩"为主线，从虚拟内存、页表、缺页中断、页回收与 Swap 机制讲起，带你完整走一遍从现象到根因、从止血到根治的排查链路，并延伸到面试高频考点。

生产环境里最隐蔽的一类故障，往往不是 CPU 打满，也不是网络抖动，而是内存悄悄被压到瓶颈后引发的 Swap 风暴。本文以一次真实的"服务雪崩"为主线，从虚拟内存、页表、缺页中断、页回收与 Swap 机制讲起，带你完整走一遍从现象到根因、从止血到根治的排查链路。

一、事故开场：半夜被叫醒的"假死"服务

某天凌晨，告警群突然炸了：核心交易服务的 P99 延迟从 30ms 飙到 8s，接口大量超时，但 CPU 利用率却显示"只有 60% 左右"。运维同学第一反应是"是不是流量突增"，可监控上看 QPS 没有明显变化。

更诡异的是：登录到机器上，top 第一眼看到的是 CPU 的 %wa（iowait）高得离谱，甚至偶尔撞到 90% 以上；而 free -h 显示内存几乎被吃光，Swap 分区已用掉一大半且还在持续增长。

重启服务能短暂恢复，但十几分钟后故障复现。这不是偶发，是一场典型的 Swap 颠簸（Swap Thrashing）。

先抛一个面试常问的问题，带着它读完本文你会更有体感：

为什么内存明明还没"用完"，系统却开始疯狂读写磁盘，导致整个服务像被冻住一样？

答案就藏在操作系统的虚拟内存与页回收机制里。

二、地基：虚拟内存到底解决什么问题

要理解 Swap 风暴，必须先理解虚拟内存（Virtual Memory）。它至少有三层价值：

  1. 隔离性：每个进程都以为自己独占一整块连续的大内存，实际物理内存是按需分配的。进程 A 的地址 0x400000 和进程 B 的 0x400000 映射到完全不同的物理页框。
  2. 扩展性：程序可以使用比物理内存更大的地址空间，暂时用不到的部分可以换出到磁盘（这就是 Swap 的由来）。
  3. 安全性：页表项（PTE）里带有权限位（读/写/执行），非法访问会被 MMU 拦截并触发段错误（SIGSEGV）。

2.1 地址翻译：从虚拟地址到物理地址

CPU 发出的地址是虚拟地址，真正访问内存前要经过 MMU（内存管理单元）翻译成物理地址：

虚拟地址 [ 虚拟页号 VPN | 页内偏移 Offset ]
                |
                v
       页表 (Page Table) 查找
                |
                v
物理地址 [ 物理页框号 PFN | 页内偏移 Offset ]

页表本身也存在内存里，多级页表（x86-64 下通常是 4 级）把一张巨大的表拆成树状结构，避免一次性占用过多连续内存。CR3 寄存器保存当前进程的页表基址，进程切换时会刷新 CR3，这就是为什么上下文切换会"切换页表"。

2.2 缺页中断：内存按需分配的核心

当你访问一个尚未映射到物理内存的虚拟页时，MMU 无法完成翻译，会触发 缺页中断（Page Fault）。内核的缺页处理程序根据情况分类：

  • Minor Page Fault（次缺页）：页在内存里，只是还没建立映射（比如访问共享库、Copy-On-Write 触发前的只读页）。代价小。
  • Major Page Fault（主缺页）：页不在内存，需要从磁盘（文件或 Swap）读入。代价大，涉及真正的 I/O。
  • Invalid Page Fault：访问了非法地址，内核直接给进程发 SIGSEGV。

Swap 风暴的本质，就是 Major Page Fault 在短时间内被海量触发，而每一次都要去磁盘搬数据，把本该是内存速度的操作拖成了磁盘速度。

三、内存不够时，内核在做什么

当空闲物理内存低于某个水位线时，内核的**页回收（Page Reclaim）**机制开始工作。理解它，就理解了故障的发动机。

3.1 水位线与 kswapd

Linux 把物理内存划分为几个水位线：

  • High：空闲内存充足，停止回收。
  • Low：开始唤醒 kswapd 后台线程异步回收。
  • Min：内存极度紧张，分配请求会直接同步回收（direct reclaim），这会阻塞当前进程，造成卡顿。

kswapd 是后台守护线程，负责在内存压力不大时"温和"地回收；一旦压力突破 min，业务进程自己就得停下来做 direct reclaim，延迟瞬间爆炸。

3.2 LRU 与回收优先级

内核用近似 LRU（最近最少使用）的链表管理匿名页和文件页，回收时遵循一个基本原则：先回收"最便宜"的。

  • 文件页（File-backed）：有磁盘副本，回收后需要时再从文件读回，相对安全。
  • 匿名页（Anonymous，堆、栈、malloc 出来的内存）：没有磁盘文件对应，要回收就必须写到 Swap 分区，这就是 Swap 写入的来源。

所以：当匿名内存（堆内存）占用越来越大，文件缓存被挤光后，内核只能把匿名页往 Swap 里搬。

3.3 swappiness：Swap 的"意愿度"

/proc/sys/vm/swappiness（默认通常是 60）控制内核"更愿意回收文件页还是匿名页"。值越大，越倾向于把匿名页 swap 出去。

注意一个常见误解：swappiness=0 不代表完全不 swap，只是极端内存压力下仍会发生。很多生产环境会把它调低（比如 1 或 10），以减少不必要的匿名页换出。

四、事故回放：Swap 风暴是怎么炼成的

把前面的机制串起来，故障链条其实非常清晰：

  1. 内存缓慢爬升：某个版本引入了缓存未设上限，或某处对象泄漏，进程的堆内存持续上涨。
  2. 文件缓存被挤占：空闲内存跌破 low，kswapd 开始回收。由于匿名内存占比高，它越来越频繁地把匿名页写入 Swap。
  3. Swap 持续写入：swappiness 偏高 + 匿名内存大，磁盘 Swap 分区被不断写入，磁盘 I/O 压力上升，%wa（iowait）抬高。
  4. 访问模式触发 Major Page Fault：进程要用的代码段/数据恰好刚被换出到 Swap，访问时触发 major page fault，必须从磁盘读回。
  5. 颠簸（Thrashing）：刚换出的页马上又要被用，又被换出，陷入"换出—换入—再换出"的死循环。CPU 大量时间花在等 I/O 和内核回收上，业务线程拿不到 CPU，延迟飙升。
  6. 雪崩：direct reclaim 阻塞关键路径，GC（如果是 Java 等带 GC 的语言）又因内存压力更频繁，进一步推高 CPU 与延迟，最终接口大面积超时。

一句话总结：不是磁盘慢，而是"用内存的地方被迫走了磁盘"，加上 I/O 等待把 CPU 也拖下水，服务就"假死"了。

五、排查工具链：从现象到根因

遇到疑似 Swap 问题，按下面这套组合拳基本能定位：

5.1 一眼看全局

# 内存与 Swap 概览
free -h

# 内存压力与缺页统计（si/so 是 swap 换入换出速率，bi/bo 是块设备 I/O）
vmstat 1

# CPU 各核状态，重点看 %wa
mpstat -P ALL 1

关键信号：

  • vmstat 里 si/so 持续不为 0 → 正在发生 Swap 换入换出。
  • %wa 持续高位 → CPU 在等 I/O，典型的 Swap 颠簸特征。

5.2 深入内存细节

# 详细内存组成
cat /proc/meminfo

# 看具体进程的内存与 Swap 占用
top -o %MEM
# 或
ps -eo pid,comm,vsz,rss,swap,%mem --sort=-%mem | head

/proc/meminfo 里值得关注的字段：

  • MemAvailable：真正可用的内存估算。
  • SwapTotal / SwapFree：Swap 总量与剩余。
  • Pages swapped in/out（/proc/vmstat）：累计 Swap 次数。

5.3 定位"罪魁"进程

# 哪个进程占了最多 Swap
for pid in $(ls /proc | grep -E '^[0-9]+$'); do
  awk -v p=$pid '/^VmSwap/{print p, $2, $3}' /proc/$pid/status 2>/dev/null
done | sort -k2 -n -r | head

找到 Swap 占用最高的进程，再结合其业务特征（是不是有无限缓存、大对象池、内存泄漏）进一步分析。

六、止血与根治：从救火到不再着火

6.1 紧急止血

# 1) 立即释放 page cache（不影响业务数据，谨慎在大流量时执行）
echo 3 > /proc/sys/vm/drop_caches

# 2) 临时降低 swap 意愿
sysctl -w vm.swappiness=1

# 3) 极端情况下可临时禁用 swap（会让内存不足时直接 OOM，需谨慎）
# swapoff -a

注意：swapoff -a 不是万能药。如果物理内存本来就不够，关掉 Swap 只会让进程更快被 OOM Killer 杀掉，可能从"慢死"变成"直接挂"。

6.2 查找内存泄漏根因

  • 若是 JVM 服务：拉 jmap/jstat、看堆转储（heap dump），定位大对象。
  • 若是 C/C++ 服务：用 valgrind、AddressSanitizer 或 tcmalloc 的 heap profiler。
  • 若是缓存无上限：给缓存加容量上限（如 LRU 淘汰、TTL、最大条目数）。

6.3 架构层面的根治

  1. 给内存设边界：容器场景务必配置合理的内存 limit，并配合 cgroup 防止单实例吃光节点。
  2. 调低 swappiness：数据库、缓存类等对延迟敏感的服务，通常调低到 1~10，甚至禁用 Swap（前提是物理内存充裕）。
  3. 合理规划 Swap：到底开不开 Swap 是个权衡。开 Swap 能在内存小幅超额时兜底（避免立刻 OOM），但也可能掩盖问题并引入颠簸；不开则故障更"干脆"。关键是监控 Swap 的使用速率，而不是有没有开。
  4. OOM Killer 调优：通过 /proc/<pid>/oom_score_adj 调整关键进程的 OOM 优先级，避免误杀核心服务。
  5. 容量与压测：上线前做内存压测，确认峰值内存有安全余量，而不是"正好够用"。

七、面试延伸：这些考点经常串起来考

Swap 这个主题，面试常和下面这些点联动：

  • 虚拟内存 vs 物理内存：为什么需要虚拟内存？它带来了隔离、扩展、安全。
  • Copy-On-Write（写时复制）：fork() 为什么快？父子进程共享页，写时才复制出新页——这也解释了为什么频繁写 fork 出的进程会触发大量页复制和缺页。
  • Major/Minor Page Fault 的区别：这是性能分析的高频题，Major 涉及磁盘 I/O，是 Swap 风暴的直接推手。
  • OOM 触发条件：不是"内存用满"才 OOM，而是分配请求在 min 水位都无法满足、且回收失败时才触发。
  • Swap 与 swappiness 的关系：swappiness 只是"意愿度"，不是开关。

一道经典追问：“你们生产上开 Swap 吗？为什么？” 没有标准答案，能讲清权衡（兜底 vs 掩盖问题 + 颠簸风险）、并结合监控策略，才是加分回答。

八、小结

Swap 风暴的本质，是内存压力 → 页回收偏向匿名页 → 持续 Swap I/O → Major Page Fault 激增 → CPU 等 I/O（%wa 升高）→ 业务线程被阻塞 的正反馈链路。排查靠 free/vmstat/top/proc 这一套组合拳定位 Swap 速率与罪魁进程；根治靠给内存设边界、调低 swappiness、修复泄漏根因，而不是简单地"重启就好"。

记住那条铁律：内存问题，别只看内存——要看 Swap、看 iowait、看缺页。 三者一起看，故障画像才完整。
